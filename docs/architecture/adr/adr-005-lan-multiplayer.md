# ADR-005 局域网多人方案（V3）

状态：Proposed｜日期：2025｜决策人：程基岩

## 上下文
原作多人基于 Steam Lobby（分析报告 §3.3：建房/大厅码/邀请、猫摆放排布、互赠礼物、CatPatter 敲击同步、Battle Royale）。复刻平台是 C# WPF 单机，Steam 生态不可用 → 替换为**局域网联机**（同网段，无公网服务器、无账号体系）。消息特征：高频小包（敲击事件 ≤ 64B，~10Hz 峰值）+ 低频大包（加入时同步房间内各猫的位置/装扮/物品清单，~10KB）。

## 备选方案

### A. 裸 UDP（自建可靠层）
- 优点：延迟最低、无连接。
- 缺点：需要自做重传/有序/心跳/NAT 穿透——为局域网场景过度工程；不可靠传输下"加入同步大包"处理复杂。排除。

### B. WebSocket + ASP.NET Core（Kestrel 宿主于房主进程）
- 优点：成熟、消息帧现成。
- 缺点：引入 ASP.NET Core 大依赖栈；房主进程变 HTTP 服务器，防火墙弹窗与端口管理更重；HTTP 升级握手对纯局域网玩具过重。排除。

### C. TCP + 自定义长度前缀帧 ✅
- 房主 `TcpListener`，客户端 `TcpClient`；消息帧 = `[u16 magic][u8 version][u8 msgType][u32 payloadLen][payload]`。
- 敲击同步走 TCP 的代价（Nagle/队头阻塞）在局域网 RTT < 1ms 下无感；**正确性远比延迟余量重要**（猫敲鼓错序比延迟 5ms 更伤）。
- `Socket.NoDelay = true` 关 Nagle。

### D. SignalR
- 优点：抽象最高。
- 缺点：依赖体积、连接生命周期黑盒、断线重连语义不可控；协议对我们不可见。排除。

## 决定
**方案 C**。

### 协议要点
- 编解码：`BongoCat.Protocol` 项目手写二进制编解码（`IBinaryEncodable`，Span-based），**不用反射序列化**——消息 ≤ 15 种，手写可控、零分配、可 fuzz 测试。
- 消息集（V3 首版）：

| msgType | 消息 | 方向 | 说明 |
|---|---|---|---|
| 0x01 | Hello { name, protocolVersion, skinHash } | C→S | 加入握手（name = 宠物名） |
| 0x02 | Welcome { yourId, roster[] } | S→C | 房间名册（各猫位置/装扮；roster[].name = 宠物名） |
| 0x03 | CatState { catId, posRel, outfit } | S→C 广播 | 摆放/装扮变更 |
| 0x04 | Tap { catId, side } | 双向 | 敲击事件，10Hz 合并上限 |
| 0x05 | Chat/Gift { from, to, itemId } | S→C 广播 | 互赠（本地库存扣减） |
| 0x06 | Kick/Bye { reason } | 双向 | 断开语义 |

- 消息上限 256KB（超限即断开，防恶意包）；`payloadLen` 读取前先校验。
- **安全边界**：局域网内所有来包按"不可信输入"处理——物品/位置/名字长度全部服务端（房主）校验；房主权威：客户端只发意图（Tap/Gift 请求），不广播状态。V1 联机**不含**经济同步，礼物只在双方本地库存各自记账，杜绝"改档刷物品进别人房间"的经济污染面。

## 补充决定：E9 宠物名（无 wire 变更，2026-11）
需求是让远端看到玩家给桌宠取的名字。评估过三种方案：

1. **Welcome/TLV 追加名字字段 + bump protocolVersion**——旧客户端在帧头版本检查即
   `Invalid → 断开`；违背"旧版本不收名字字段也不崩"；
2. **新增 NameSync 消息类型**——旧客户端对未知 msgType 同样按非法帧断开；
3. **复用既有名册 `name`（UTF-8 长度前缀）字段承载宠物名，不 bump、不新增字段** ✅。

选 3：新客户端把宠物名清洗到 ≤24B 后填进 Hello/名册的既有 name 字段，服务器（哑中继）
原样转发；旧客户端只当普通显示名展示，旧→新方向新客户端也接受 48B 旧显示名并在展示层
清洗。代价是"名字字段的语义"从显示名升级为宠物名，以及房间内改名不做实时广播
（对端下次进入房间收到新 Welcome 时生效）——用最小的协议侵入换完整双向兼容。
因此第 44 行"版本不匹配即拒绝"的既往规则在本扩展中**不触发**：帧版本仍为 1。

### 大厅发现
- 不做 UDP 广播发现（增加攻击面与复杂度）；用**房间码**（房主 IP:port 编码成 6 位短码 + 端口直连），与原作"大厅码加入"体验同构。

## 后果
- `INetLobby` 接口（module-map）隔离传输细节；单机模式零网络代码路径（DI 不注册）。
- Battle Royale 等玩法（原作有）**超出 V3 首版**：仅同步敲击与摆放，BR 需要房间状态机（倒计时/淘汰），列为 V3+ 备选，不在协议首版预留复杂字段，用 msgType 空间扩展。
- 断线策略：心跳 2s 间隔、5s 超时踢出；房主退出 = 房间解散（明确提示，不做房主迁移——YAGNI）。
- 协议变更以 `protocolVersion` 拒绝不匹配客户端，消息不向前兼容。
